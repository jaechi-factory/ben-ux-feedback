# 설계 결정

이 스킬을 왜 이렇게 만들었는지 정리한 문서예요. 초기 설계에서 바꾼 점, 심각도, 페르소나, 리포트 구조, 보안 결정을 다뤄요. 판단 기준 자체는 `skill/ben-ux-feedback/references/`가 정본이에요.

## 초기 설계에서 유지한 것

- **화면에 보이는 것만 지적해요.** 추출한 텍스트, DOM, 콘솔은 보조 근거라서 `evidence.type`으로 따로 표시해요.
- **근본 원인과 바로 쓸 수정안을 강제해요.** `why`, `fix`, `asis`, `tobe`가 맡고, 심각 지적은 `tobe`가 필수예요.
- **쓰기 금지.** Figma와 라이브 서비스를 바꾸는 동작은 하지 않아요.
- **제외 규칙은 사용자가 켜요.** 팀마다 다른 확정 사항은 `run.exclusions`의 선택 규칙(`curly-braces`, `dummy-amount-mismatch`)으로 바꿨어요.
- **많은 화면은 나눠서 써요.** `review-part-N.json`을 합치고 모든 화면을 빠짐없이 봤는지 검사해요.
- **판정 절차.** 화면 유형 판별, 화면 계약, 결정 품질, 상태와 되돌림, 실패 방식에서 제품 리스크로 이어지는 진단, 추상 표현 금지, 빠진 흐름 8종 점검, 화면 간 일관성 점검을 가이드라인 용어로 다시 썼어요.
- **검증 로직 일부.** 중복 지적 경고, `asis` 인용이 추출 텍스트에 있는지 보는 환각 경고, 화면 이미지 경로 이탈 차단을 살렸어요.
- **입력 판별과 Figma 캡처.** Figma 브랜치 주소 처리, 치수가 비슷한 프레임 묶기로 화면 감지, 커넥터 기반 연결, 항상 다시 렌더링하는 방식을 유지했어요.

## 초기 설계에서 바꾼 점

| 초기 설계 | 지금 |
|---|---|
| 핵심 4, 보조 4 원칙 체계 | 가이드라인 한 문서(`guideline.md`)로 일원화 |
| 브랜드 인용 가능/금지 목록 | 가이드라인의 고지와 한계 절, `NOTICE.md` |
| 설정 파일을 뒤져 Figma 토큰 찾기 | `FIGMA_TOKEN` 환경 변수만 읽기 |
| 특정 앱의 도구 이름과 개인 운영 용어 | 어떤 환경에서도 읽히는 중립 표현 |
| finding 필드 `root_cause`, `problem`, `priority`, `pin`, `evidence_type` | `why`, `observation`, `severity`, `evidence{}` (`pin`은 리포트 단계에서 정해요) |
| 가상 UT 없음 또는 연령대 표 | 연령대 × 디바이스 적응도 × UX 이해도 페르소나와 화면별 세 축 판정 |

**숫자 등급 대신 세 단계 말 등급을 쓴 이유.** 숫자 등급은 몇 번째가 어디까지인지 사람마다 해석이 달라서, 심각, 중간, 낮음 세 단계의 쉬운 말로 바꿨어요. 숫자 등급 값은 검증기가 오류로 거절해요.

## 심각도 3단계

심각, 중간, 낮음만 써요. 숫자 등급은 몇 번째가 어디까지인지 사람마다 달라서 쉬운 말로 줄였어요. 리포트 배지에는 행동이 보이는 말을 같이 붙여요.

- 심각: 먼저 고쳐요
- 중간: 고치면 좋아요
- 낮음: 여유 있을 때 봐요

심각 지적에는 수정 후 모습(`tobe`)이 필수이고 고쳤는지 확인하는 기준(`done_when`)을 권해요. "고치라"로 끝나는 지적을 막으려는 결정이에요.

## 페르소나 구조

연령대(청년, 중년, 노년)별로 능력이 다르다는 전제로, 페르소나를 **연령대 × 디바이스 적응도(상·중·하) × UX 이해도(상·중·하)** 로 나눠요.

- 기본은 서로 다른 연령대 3명이에요. 사용자가 인원이나 속성을 정하면 그대로 따라요.
- 화면마다 세 축을 판정해요: 디바이스(`device`), 시안 이해(`design`), 문구 이해(`writing`). 값은 쉬움, 보통, 막힘뿐이에요.
- 그 사람 말투의 한마디(`quote`)를 남기고, 막힘이면 원인(`cause`)을 적어요. 참을 수 있는 정도를 넘으면 그 화면에서 이탈해요.
- 막힘과 보통 반응은 지적(`findings[].id`)에 이어요. 기존 지적이 없으면 새 지적을 만들고 `from_ut`로 표시해요. 화면과 흐름 문제는 가이드라인 원칙으로, 문구 문제는 문구 기준으로 수정안을 써요.
- 점수, 완주율, 시간 같은 수치는 만들지 않아요. 정적 화면에서 추론한 값이라 숫자로 쓰면 실제 조사처럼 읽히기 때문이에요. 결과에는 항상 "가상 사용자 반응 · 실제 조사 아님"을 표시해요.
- 아직 근거가 약한 부분: 시안 이해(`design`)는 기기 다루기와 말 이해에서 추정해 넣은 칸이에요. 확정된 근거가 있는 값이 아니에요.

## 리포트 구조

메이커가 읽고 바로 고치는 흐름을 기준으로 했어요.

- **첫 화면**: 총평 한 줄과 "먼저 고칠 것"(심각 우선, 최대 3개). 화면·지적·심각 수는 그 아래 작은 한 줄이에요. `report.md`도 같은 규칙을 써요.
- **지적 카드 순서**: ① 무엇이 문제인가 ② 사용자에게 생기는 일(연결된 가상 사용자 반응) ③ 이렇게 고쳐요(수정 전과 후를 나란히, 복사 버튼) ④ 근거(원칙, 사례 링크, 확인하지 못한 것) ⑤ 고쳤는지 확인하는 기준. 비어 있는 부분은 통째로 빼요.
- **정리 기능**: 화면마다 [문제를 해결했어요], [문제가 아니에요], [되돌리기]가 있고 상단 필터 칩으로 숨겨요. 선택은 그 브라우저에만 저장해요. [남은 지적을 체크리스트로 복사]는 정리한 화면을 뺀 `- [ ]` 목록을 만들어요.
- **빠진 흐름**은 화면에 묶이지 않는 지적을 따로 모은 섹션이에요.
- **가상 UT 섹션**은 `ut`가 있을 때만 나와요. 페르소나 카드와 페르소나 × 화면 표를 보여 주고, 표는 좁은 화면과 화면이 많을 때 페르소나별 카드로 쌓여요. 의미를 색에만 맡기지 않고 글자와 점 모양을 함께 써요.
- **연령대 아이콘**은 직접 그린 인라인 SVG이고 외부 파일이나 남의 일러스트를 쓰지 않아요. 이 저장소 작업물이라 MIT로 함께 배포돼요.
- **디자인**: 본문 17px, 최대 폭 880px, 섹션 간격 72px, 그룹 사이 간격이 그룹 안 간격보다 커요. 버튼은 기본 `button`, 키보드 포커스 표시, 이미지 대체 텍스트, 건너뛰기 링크, 줄인 모션 설정을 지켜요. 대비는 손으로 계산했고 도구로 재지 않았어요.
- 형식을 바꿀 때는 `references/output-contract.md`를 먼저 고치고 검증기와 빌더를 맞춰요.

## 속도 개선 (0.2.0)

실제 사용에서 시간이 가장 많이 든 곳은 도구 호출이 아니라 범위를 잘못 잡아 다시 한 판정, 매번 새로 쓴 비교용 HTML, 파일마다 따로 한 읽기 왕복이었어요. 판정 기준과 지적 규율은 그대로 두고 이 세 곳만 줄였어요.

- **0단계 범위 확인**: 받은 화면의 형제 화면을 먼저 한 번 조회하고 모드를 정해요. 한 장만 보고 나서 나머지를 다시 보는 일을 막아요. 자동으로 넓히는 범위는 같은 목적의 시안까지만이라, 다른 단계 화면까지 끌어와 오히려 느려지지 않아요.
- **비교 모드와 고정 틀**: 시안 비교는 `compare.json` 내용만 쓰고 `build_compare.py`가 검사와 HTML을 맡아요. 레이아웃 설계와 CSS 작성, 매번 하던 화면 확인이 없어져요. 틀의 구조와 안전성(이스케이프, 외부 요청 없음, 전수 커버리지)은 테스트로 지켜요. 지적 항목은 단일 모드와 같은 필드(위치, 심각의 수정 후 모습, 원칙과 사례)를 받고, 검사 규칙은 `validate.py`를 그대로 불러 써서 두 모드의 기준이 갈라지지 않아요.
- **묶어 읽기**: 모드별 필수 파일을 한 번의 호출로 읽어요. 단일·흐름 모드의 읽는 파일은 이전과 같아요. (0.2.1에서 파일별 병렬 읽기로 바꿨어요. 아래 참고)
- **짧은 채팅 답**: 리포트가 있으면 채팅에는 총평, 먼저 고칠 것, 경로만 써요.
- 비교 모드의 가상 UT는 1위 시안 한 장만 걸어 봐요. 시안 전부를 걸으면 시간이 시안 수만큼 늘고, 시안 사이 차이는 기준별 비교가 맡아요. 끄면 리포트 끝에 생략했다고 자동으로 적혀요.

## 속도 개선 (0.2.1)

0.2.0을 실제로 돌려 보니 브리프 양식이 보이기까지 30초 넘게 걸렸어요. 원인은 양식을 묻는 답변 안에서 기준 문서를 먼저 읽고 나서 양식을 내보내게 한 순서였어요. 글은 도구보다 먼저 화면에 보이는데, 읽기를 글 앞에 두면 사용자는 읽기가 끝날 때까지 빈 화면을 봐요. 거기에 셸 명령 하나로 여러 파일을 이어 붙여 읽다가 출력 한도를 넘어 다시 읽은 왕복과, ben-ux-writing의 기준 파일 이름을 몰라 따로 읽은 왕복이 더해졌어요.

- **양식 먼저, 읽기는 같은 턴 뒤에서**(0.2.2에서 되돌렸어요. 아래 참고): 브리프를 묻는 답변은 양식을 첫 글로 내보내고, 그 뒤 같은 답변 안에서 기준 문서 읽기, 수집, 화면 이미지 열기를 병렬로 끝내요. 끝나면 "열어 뒀어요" 한 줄만 붙여요.
- **진행 알림과 결론 먼저**: 도구를 부르는 턴마다 첫 글 한 줄로 지금 하는 일을 말해요. 가장 오래 걸리는 JSON 쓰기 턴은 총평과 먼저 고칠 것 3개를 먼저 내보낸 뒤 써요. 사용자는 결과 파일이 나오기 전에 결론을 먼저 봐요. 마지막 답은 경로와 달라진 점, 확인 못 한 것만 써서 되풀이하지 않아요.
- **턴 예산**: 준비(수집 + 기준 문서 + 이미지, 병렬) → 결론 + JSON 쓰기 → 검증과 리포트 한 명령. 폴더 입력(목록을 봐야 함)과 Figma·라이브(형제 조회 → 렌더 → 저장)는 한두 턴이 더 들어도 돼요.
- **읽기 방식**: 파일별 읽기 도구를 같은 턴에 병렬로 불러요. 셸로 이어 붙여 출력하지 않아요. ben-ux-writing의 기준 파일 이름(01, 02, 07, 피드백용 06)을 SKILL.md에 직접 적어서 그 스킬의 SKILL.md를 먼저 열어 보는 왕복이 없어요.
- **입력 판별 생략**: 이미지 파일이나 폴더가 분명하면 `detect_input.py`를 건너뛰고 `image_capture.py`로 바로 가요. 같은 검사를 하기 때문이에요. `image_capture.py`는 shot 경로를 출력해서 폴더 입력이 `capture.json`을 다시 읽는 턴을 쓰지 않게 해요.
- **dry run으로 찾은 공백**: 샘플 화면 3장으로 끝까지 돌려 보니 흐름은 준비 → 이미지(폴더) → JSON → 검증+리포트 4턴, 검증 재시도 0회였어요. 대신 지침 공백이 확인 턴을 만들었어요. 지적 없는 화면은 HTML에 이미지가 들어가지 않는다는 설명, `appendix.md`를 언제 펼치는지(procedure.md와 SKILL.md가 달랐어요), 지적 없이 확인 필요만 있는 화면의 verdict 쓰는 법을 적어 넣었어요.
- **검증 왕복 줄이기**: JSON을 쓰기 전 자가 점검 목록을 두고, 통과하면 `validate.py && build_report.py`로 리포트까지 한 번에 가요. JSON은 셸 heredoc이 아니라 파일 쓰기 도구로 써요.
- **가상 UT 경량화**: 세 축이 모두 쉬움인 화면은 step을 쓰지 않고 walk의 `easy_screens`에 id만 적어요. 할 말이 없는 화면에 한마디를 지어내지 않게 되고, 쓰는 양이 줄어요. 모든 화면이 쉬운 페르소나는 `steps`를 비우고 완주로 적어요. 한마디를 지어내지 않으려는 것이고, 화면 1장 단일 모드에서도 경량화가 동작해요(이탈 walk는 멈춘 화면 step이 있어야 해요). 리포트는 그 칸을 "세 가지 모두 쉬움"으로 보여요. 양식 아래에 가상 UT를 뺄 수 있다는 한 줄을 붙여 사용자가 속도를 고를 수 있게 했어요. 세 명, 세 축, 막힘 연결 규칙은 그대로예요.
- **이미지 재열기 금지**: 준비 턴에 열어 둔 이미지가 대화에 남아 있으면 근거 재확인과 가상 UT에서 다시 열지 않아요. 지적마다 또는 페르소나마다 shot을 다시 여는 턴이 생기지 않게 하려는 거예요. 대화가 요약돼 사라졌을 때만 다시 열어요.
- 판정 기준, 지적 규율, 출력 계약의 다른 필드는 바꾸지 않았어요.

## 속도 개선 (0.2.2)

0.2.1의 "양식 먼저, 읽기는 같은 턴 뒤에서"를 새 세션에서 실측했어요. 양식은 도구보다 먼저 나왔지만(30.6초 양식, 31.2초 첫 읽기) 양식까지 30초가 걸렸고, 그중 입력 처리는 약 6초, 나머지 약 24초는 양식 뒤에 붙일 읽기 11건과 마무리 줄을 계획하는 생각이었어요(첫 응답 출력 3,177토큰. 양식만 낼 때는 수백 토큰이에요). 모델은 턴의 첫 글자를 내보내기 전에 그 턴 전체를 계획하기 때문에, 양식 뒤에 일을 붙이면 그 계획 시간이 양식 앞에 붙어요. 양식 뒤 읽기는 9초, 마무리 줄은 8.6초가 더 걸렸고, 마무리 줄은 환경 내부 폴더 이름까지 들춰 군소리가 됐어요.

- **묻는 턴은 양식만**: 브리프를 물어야 하면 도구 호출도 판단도 마무리 줄도 없이 양식만 출력하고 턴을 끝내요. SKILL.md 맨 위 "첫 행동"에 이 분기를 두어 나머지 지침을 읽기 전에 결정하게 했어요.
- **읽기는 답 뒤 준비 턴에**: 수집, 기준 문서, 화면 이미지를 답을 받은 다음 턴에 병렬로 열어요. 0.2.1보다 답 뒤 경로가 읽기 한 턴(약 9초)만큼 길어지지만, 양식은 수십 초 빨리 보이고 사용자가 쓰는 동안 턴이 끝나 있어 어느 UI에서든 바로 답할 수 있어요.
- 턴 예산은 그대로 3번(준비 → 결론 + JSON → 검증과 리포트)이고, 묻지 않는 경우에는 첫 턴이 준비 턴이에요.

## 리뷰 맥락(브리프)

화면만으로는 "잘 만들었나"까지만 판정할 수 있어요. 무엇을 풀려는 화면인지 모르면 해결책이 문제와 어긋나도 잡지 못해요. 그래서 판정 전에 제품, 목표, 문제, 원인, 해결 방법, 유저·회사 기대효과를 짧게 받아요.

- 묻는 건 한 번뿐이고, 묻는 턴은 양식만 출력하고 끝내요. 읽기와 수집은 답을 받은 다음 턴에 해요(0.2.2. 위 "속도 개선 (0.2.2)" 참고).
- 이미 답한 항목은 다시 묻지 않고, 건너뛰면 추론해서 진행하고 추론했다고 밝혀요.
- 브리프는 만든 사람의 전제예요. 지적 근거로 옮기지 않고, 화면과 다르면 화면이 이겨요. 회사 기대효과가 유저 기대효과와 부딪히면 거절 가능성을 먼저 봐요.

## 보안 결정

- **Figma 토큰은 `FIGMA_TOKEN` 환경 변수에서만** 읽어요. 설정 파일을 뒤지지 않고 토큰을 출력하거나 기록하지 않아요. 읽기 전용 토큰이면 충분해요.
- **읽기 전용**: Figma와 서비스에 쓰지 않고 로그인, 결제, 삭제 같은 상태 변경 동작을 하지 않아요.
- **화면 속 글은 데이터**예요. 이미지 안에 명령처럼 보이는 문장이 있어도 따르지 않아요.
- **HTML 리포트**: 모든 문자열을 이스케이프하고, 외부 네트워크 요청과 CDN이 없어요. 콘텐츠 보안 정책 메타 태그로 외부 로드를 막아요. 이미지는 `RUN/shots/` 안의 이미지 확장자 파일만 안에 담고, 절대 경로, `..`, 심볼릭 링크 탈출은 거절해요.
- **마크다운 리포트**: 화면에서 읽어 온 글의 문법 문자를 이스케이프하고 `http://`, `https://`는 자동 링크가 되지 않게 끊어요.
- **Figma 파일 키**는 URL 경로에 넣기 전에 인코딩해요.
- **이미지 재실행**: 같은 실행 폴더에 다시 돌리면 이번 입력에 없는 옛 이미지만 지우고 이미지가 아닌 파일은 건드리지 않아요.
- **설치 스크립트**: 기본은 계획만 출력하고 `--apply`가 있어야 복사해요. 이미 있는 폴더는 `--replace-with-backup` 없이는 덮지 않고, 있으면 `.ben-ux-feedback-backups/`로 옮겨요. 홈 폴더, 루트, 시스템 폴더, 심볼릭 링크는 거절해요.
- **생성물 일치**: `build-manifest.json`에 생성물의 SHA-256을 남기고 `build.py --check`가 정본과 다르면 실패해요.

## 계약에서 정한 것

- 마크다운 출력은 같은 필드를 읽기 좋게 재배치해요(총평과 검토 조건이 맨 위, `severity`가 제목 앞, `evidence.where`가 "화면" 줄).
- `strengths[]`는 `{note, principle, screen_id}`, `checks_needed[]`는 `{what, how}`, `summary.top`은 finding id 목록이에요.
- `screen_id`가 `null`인 지적은 `lens=흐름`만 허용해요.
- `principle` 이름은 가이드라인의 표와 목록에서 읽고 대소문자와 공백을 무시해 비교해요.
- 검증은 오류(exit 1)와 경고(`--strict`일 때만 실패)로 나눠요. 판단이 필요한 규율은 경고예요. 경고 항목은 휴리스틱이라 PASS가 곧 좋은 지적은 아니에요.

## 아직 확인하지 못한 것

- 실제 Figma API로 돌려 본 결과, 브라우저에서 보이는 리포트 모양(모바일 카드 쌓기, 복사 버튼, 아이콘 크기), 라이브 서비스 탐색은 충분히 시험하지 않았어요.
- 검증기의 단어 기반 경고(금액 불일치, 추상 수정안)는 오탐과 누락이 있을 수 있어요.
- ben-ux-writing 연동은 그 스킬의 일부 문서만 보고 맞췄어요. 설치된 환경에서의 동작은 더 확인이 필요해요.
