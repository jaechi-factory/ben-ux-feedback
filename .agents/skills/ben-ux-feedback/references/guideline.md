# 디자인 원칙 가이드라인

> **고지**: 토스의 공개 자료(toss.tech, Simplicity 컨퍼런스 등)를 학습해 만든 독립 가이드예요. 토스(비바리퍼블리카)와 제휴하거나 보증받은 관계가 아니에요. 원칙 이름과 정의 인용의 출처는 각 항목(부록 포함)에 적었어요. 라이선스는 MIT예요.

## 작업 유형별 최소 읽기
- **문구만 고칠 때**: 1절, 5-1, 5-2, 부록 15절. 문장 규칙은 ben-ux-writing(1절 참고).
  - 시작 전 질문 5개 중 1·2번만 적는다.
- **화면 기획·구현할 때**: 1절, 2절, 3절 전체. 해당 원칙의 부록만 펼친다.
  - 끝나기 전에 해당 원칙만 4절 QA 표로 자가 점검한다.
- **QA 리뷰할 때**: 1절, 4절 전체, 5절. 3절은 원칙 이름을 찾을 때만 본다.
  - 정적 화면에서 못 보는 신호는 `[확인 필요]`로 분리한다.
- 어느 경우든 우선순위(1절)와 한계(6절)는 지킨다.

토스 공식 제품 원칙과 공개 사례 178건(`cases.md`)을 바탕으로 만든 가이드예요. Claude Code, Codex, ChatGPT 같은 어떤 LLM에서든 디자인(시안·UX) 작업을 지시하고 리뷰하고 검수할 때 기준으로 써요. 매 작업마다 위 "작업 유형별 최소 읽기" 범위를 읽고, 상세 규칙·위반 신호·근거 사례 번호(`C###`)는 `appendix.md`에서, 사례 요약과 출처는 `cases.md`에서 필요할 때만 펼쳐요.

## 1. 목적과 적용 범위

- 회사 제품과 개인 제품을 가리지 않고 모든 디자인(시안·UX) 작업의 지시·리뷰·검수 기준으로 쓴다.
- **3절(작업 기준)**: 화면 기획, UI 구현, 문구, 리포트 같은 모든 디자인 작업을 시작하고 진행할 때 쓴다.
- **4절(QA 기준)**: 만든 화면이 원칙에 맞는지 독립 리뷰어가 리뷰·검수할 때 쓴다.
- 이 문서는 "무엇을 왜 이렇게 설계하나"의 판단 기준만 맡는다. 아래는 대체하지 않는다.
  - 시각 토큰과 컴포넌트는 각 제품의 디자인 시스템을 따른다.
  - UX 문구의 문장 규칙은 공개 오픈소스 스킬 ben-ux-writing(https://github.com/jaechi-factory/ben-ux-writing)을 문구 판정 기준으로 따른다. 설치돼 있지 않으면 5-1 점검만 하고 문장 세부는 확인 필요로 남긴다.
  - 리포트·문서 같은 산출물의 제작 방식은 각 팀의 제작 기준을 따른다.
- **우선순위**: 사용자 지시 · 확인된 제품 사실 · 접근성/플랫폼 제약 > 이 가이드라인 > 개별 패턴(사례).
- 충돌하면 위 순서로 고르고, 이 가이드라인을 따르지 않은 이유를 한 줄로 남긴다.
- 토스 금융 맥락을 그대로 옮기지 않는다. 사례의 `[금융·규제]`, `[업무도구]` 판단은 내 제품에 같은 조건이 있을 때만 쓴다.
- 사례의 전환율 같은 수치는 근거로 옮기지 않는다. 사례는 판단 방식을 배우는 용도다.

## 2. 핵심 사고방식

모든 원칙은 Simplicity(단순함) 하나로 모인다. 사용자가 치르는 비용을 세 가지로 보고 줄인다. **인지 비용**은 이해하고 판단하느라 드는 생각이고, **심리 비용**은 하기 싫거나 불안한 마음이고, **노동 비용**은 입력·이동·기다림 같은 수고다. Simplicity는 요소를 적게 두는 것이 아니라 이 세 비용을 사용자 대신 제품이 치르는 것이다. Simplicity를 core principle로 두고 세 비용과 세 묶음(1초 만에 이해되게·하고 싶게·하기 쉽게)으로 원칙을 나눈 것은 토스 공식 글(toss.tech mydoc, 2023-09-03)의 구조다.

원칙은 체크박스가 아니라 판단 질문이다. 질문에 "예"라고 쓰는 것으로 끝나지 않고, 이 제품의 이 화면에서 실제로 어떻게 보이는지로 답한다. 원칙 이름을 근거로 억지로 지적하거나 설계를 정당화하지 않는다.

## 3. 작업 기준

### 시작 전 질문 5개
이 절차와 심각도 체계는 공식이 아니라 이 가이드라인의 운영 설계다(바탕: 부록 16절 M8). 작업을 시작하기 전에 답을 한 줄씩 작업 메모(리뷰 파일이나 작업 문서)에 적는다. 답이 비면 사용자에게 묻거나 "확인 필요"로 남긴다. 완료 전에는 해당 원칙만 아래 4절 QA 표로 자가 점검한다.

1. 이 제품의 핵심 가치는 무엇인가?
2. 이 화면의 단 하나의 목표는 무엇인가?
3. 사용자가 이 화면에서 치르는 비용은 무엇이고, 인지·심리·노동 중 어디가 가장 큰가?
4. 없애도 되는 것은 무엇인가? (질문, 단계, 기능, 설명)
5. 사용자는 어디서 오고, 다음에 무엇을 하는가?

### 설계 중 원칙
2023판 14개와 2025판 10개를 합쳤다. 2025판 10개는 대부분 2023판과 같은 이름이라 한 항목으로 적었다(Simple Policy↔Less Policy는 미확정). 아래 질문은 공식 검토 질문을 쓰기 쉽게 줄인 것이고 원문과 출처는 부록에 있다. (2025판에서 빠진 항목은 `2023만`으로 표시)

**인지 비용: 1초 만에 이해되게**
- **Casual Concept**: 어려운 개념을 친숙하고 쉽게 만들었는가?
  모르는 이름·분류·숫자 기준을 보여줄 때는 사용자가 이미 아는 대상이나 일상 범주에 연결한다. 새 인터랙션보다 사용자가 아는 표준 컴포넌트를 먼저 고른다.
- **One Thing** (One thing per One page): 한 화면에 하나의 명확한 목표만 있는가?
  화면이 여러 행동을 담을 때는 사용자가 먼저 하려는 행동 기준으로 묶고, 주 목표 하나만 시각 무게를 준다. 부가 정보는 삭제가 아니라 한 단계 뒤로 보낸다.
- **Clear Action** (Clear CTA): 완료에 필요한 행동이 한눈에 보이는가?
  버튼 이름은 동사와 즉시성이 읽히게 쓰고, 누른 뒤 결과가 문구와 정확히 일치하게 한다. 주변 화면 없이도 무슨 일이 일어날지 알 수 있어야 한다.
- **Simple Policy** (Less Policy): 사용자가 "알아야 할" 것을 없앨 수 있는가?
  선택지의 결과가 사용자에게 차이가 없으면 묻지 말고 기본값이나 정책으로 정한다. 화면을 고치기 전에 정책·상품을 바꿀 수 있는지 먼저 따진다. 정책·기능 변경은 직접 하지 말고 제안으로 남긴다(사용자 지시·확인된 사실이 우선). (두 이름이 같은 원칙인지는 미확정이다.)
- **Easy to Answer**: 모든 질문에 3초 안에 답할 수 있는가?
  방식을 고르게 하지 말고 사용자가 지금 아는 사실을 묻는다. 어려우면 추천하고, 기억 안 나는 정보는 불러오고, 이미 가진 정보는 다시 묻지 않는다.
- **Minimum Features**: 이 기능 없이는 목표를 달성할 수 없는가?
  사용자가 머뭇거리는 단계는 빠르게 만들 방법보다 없앨 수 있는지부터 묻는다. 기능 추가는 최후의 수단이고, 큰 기능 전에 가장 싼 수단으로 수요를 확인한다. 기능 변경은 제안으로 남긴다.

**심리 비용: 하고 싶게**
- **Explain Why**: 왜 이 과업을 해야 하는지 충분히 설명했는가?
  동의·권한·정보를 요청할 때는 왜 지금 필요한지 먼저 말하고, 미리 체크하지 않고, 쉽게 거절할 출구를 둔다. 설명 화면을 더하기 전에 이름 변경이나 직접 체험 같은 대안을 먼저 본다.
- **Value First**: 뭐가 좋은지 보이기 전에 입력이나 비용을 요구하지 않는가?
  줄일 수 없는 긴 입력·인증 앞에서는 얻을 이익을 먼저 보여준다. 가치를 체감한 직후에 동의나 비용을 묻는다.
- **Context Based**: 앞뒤 상황의 맥락이 이어지는가?
  알림과 화면은 사용자의 그 순간 상황에 맞춘다. 확인되지 않은 상황으로 불안을 만들지 않고, 새 기능은 사용자가 이미 쓰는 장소에 둔다.
- **No Ads Patterns** (2023만): 습관적으로 광고 문법으로 소구하고 있지는 않은가?
  클릭을 유도하는 문구는 누른 뒤 결과와 일치하게 쓴다. 이탈 안내는 잃을 것을 경고하지 않고 사실만 남긴다. 근거 사례가 4건뿐이라 근거가 약하다.
- **Personalize** (2023만): 고객에게 맞춤 경험을 제공했는가?
  사용자가 모르는 값은 이미 가진 이력이나 역할로 후보를 채우고 선택만 하게 한다. 추천이 틀릴 수 있으면 후보를 확률순으로 모두 보인다.

**노동 비용: 하기 쉽게**
- **Sleek Experience** (2023만): 전체 흐름이 물 흐르듯 진행되는가?
  복사·붙여넣기나 도구 간 이동이 있으면 한 화면의 검색·선택으로 끝나게 한다. 입력 화면은 값에 맞는 키보드로 열고, 유일한 할 일이 입력이면 바로 포커스를 준다.
- **Low-cost Action** (2023만): 노동 비용이 더 적게 드는 경험인가?
  사용자가 대신 해야 하던 확인·계산·재입력은 제품이 아는 정보로 대신한다. 해결이 다른 곳에 있으면 문구 안내로 끝내지 말고 행동 버튼을 붙인다.
- **No More Loading**: 핵심 흐름에서 기다림을 없앴는가?
  긴 대기는 대기 화면을 꾸미기 전에 기다릴 필요가 없는 구조인지 먼저 본다. 기다려야 하면 빈 로딩 대신 믿을 수 있는 실제 정보를 보여준다.

### 원칙 밖 메타 패턴 (옮길 가치가 큰 것 6개)
- **관찰이 말보다 먼저(M1)**: 사용자의 "괜찮다"를 믿지 않고 행동을 보며, 제작자 직관을 의심한다.
- **싸게 검증하고 되돌릴 수 있게(M2)**: 큰 것을 만들기 전에 프로토타입·시트·점진 배포로 확인하고, 틀렸을 때 돌아가는 비용을 따진다.
- **지표는 쌍·세그먼트·정성으로(M3)**: 지표가 좋아도 정성 신호를 무시하지 않고, 어떤 사용자가 빠졌는지 확인한다.
- **보호와 거절 가능성(M4)**: 다크패턴을 쓰지 않고, 자동화는 사용자가 결과를 책임지는 지점까지만 한다.
- **원인을 거슬러 제거(M6)**: 같은 화면을 여러 번 고쳐도 안 풀리면 시안을 멈추고 정책·구조를 먼저 본다. 개선보다 제거를 택하되, 정책·기능 제거는 제안으로 남긴다.
- **기준을 먼저 세우기(M8)**: 시안 전에 중요도 순위와 핵심 가치 한두 개를 정한다.

### 원칙이 부딪힐 때의 우선순위
1. 사용자의 거절 가능성 > 단기 전환. 거절을 쉽게 해도 동의율이 오른 사례가 있다.
2. 자동화 범위는 사용자가 결과를 책임지고 인지할 수 있는 지점까지다. 효율 최대 지점이 아니다.
3. 줄이기 vs 정보 완전성: 줄일 수 없는 내용은 고정하고 위계·순서·전달 방식을 바꾼다.
4. 설명 줄이기 vs 설명 더하기: 반복되는 말은 빼고, 동의·낯선 연락·새 개념처럼 불안한 지점은 설명을 먼저 둔다.
5. 가치 화면 추가 vs 단계 제거: 줄일 수 없는 긴 퍼널일 때만 가치 화면을 더하고, 새 정보가 없는 안내는 걷어낸다.

## 4. QA 기준

### 절차
이 절차는 공식이 아니라 이 가이드라인의 운영 설계다(바탕: 부록 16절 M8). 리포트는 리뷰 파일에 남긴다.
1. 제품 핵심 가치와 화면 목표를 한 줄로 먼저 적는다.
2. 화면을 직접 보고, 원칙을 보기 전에 관찰을 적는다.
3. 아래 원칙별 위반 신호로 관찰을 대조한다.
4. 지적마다 화면 근거(파일·위치)를 다시 확인한다.
   - 화면에서 보이지 않는 것(동작, 애니메이션, 데이터 출처, 법무 판단)은 "확인 필요"로 분리한다.
   - 횟수·잘림·크기·수량은 화면에서 직접 세고 확인한 것만 쓴다. 과장과 추정 수량을 쓰지 않는다.
   - 원칙 이름을 맞추려고 억지로 연결하지 않는다. 연결이 약하면 원칙을 빼고 관찰만 적는다.
5. 심각·중간·낮음으로 심각도를 매긴다.

### 원칙별 QA 질문 표
`[확인 필요]`가 붙은 신호는 정적 화면만으로 볼 수 없고 데이터·이력·동작이 있어야 확인된다.

| 원칙 | 질문 | 관찰 가능한 위반 신호 |
|---|---|---|
| Casual Concept | 모르는 이름·숫자 기준이 아는 말로 바뀌었는가? | 전문 용어·숫자 기준이 그대로 노출됨. 문구를 가리면 무엇인지 모름 |
| One Thing | 이 화면의 목표가 한 문장으로 말해지는가? | 우선순위가 부딪히는 구좌가 계속 늘어남 `[확인 필요]`. 한 면에 같은 비중의 수단이 여럿 |
| Clear Action | 누르면 무슨 일이 생기는지 버튼만 봐도 아는가? | 버튼 이름이 주변 맥락에 기댐. CTA가 광고처럼 보여 지나쳐짐 |
| Simple Policy | 사용자가 몰라도 되는 선택·조건이 남아 있는가? | 결과가 같은 선택을 매번 물음. 옛 정책 때문에 남은 요구 `[확인 필요]` |
| Easy to Answer | 모든 질문이 3초 안에 답해지는가? | 방식을 고르게 함. 이미 가진 정보를 다시 물음. 빈칸에서 오래 멈춤 `[확인 필요]` |
| Minimum Features | 빼도 목표를 달성하는가? | 쓰이지 않는 레이아웃·안내가 남음. 몰라도 되는 내부 개념이 노출됨 |
| Explain Why | 요청하는 지점에서 이유를 말하는가? | 미리 체크된 동의. 이유 없는 권한·재동의 팝업 |
| Value First | 비용을 묻기 전에 이익이 보였는가? | 긴 입력·인증 앞에 이익 화면이 없음. 눌러도 "내역 없음" `[확인 필요]` |
| Context Based | 이 사용자의 그 순간 상황에 맞는가? | 상황과 안 맞는 알림(매출 0원인데 매출 알림). 사용자가 쓰는 장소를 벗어난 기능 |
| No Ads Patterns | 문구의 약속과 누른 뒤 결과가 일치하는가? | 문구와 결과 불일치. 이탈 안내가 손해 프레임 |
| Personalize | 아는 정보로 후보를 좁혔는가? | 전체 목록에서 직접 찾게 함. 이미 가진 정보를 다시 물음 |
| Sleek Experience | 사용자가 도구 사이를 오가거나 복사하는가? | 복사·붙여넣기 반복. 값과 키보드 종류 불일치 |
| Low-cost Action | 제품이 대신할 수 있는 수고가 남았는가? | 불안해서 앱 밖에서 확인함 `[확인 필요]`. 해결 행동은 다른 곳인데 문구만 있음 |
| No More Loading | 핵심 흐름에서 기다림이 있는가? | 사용자가 기다려야 하는 단계 `[확인 필요]`. 빈 로딩 이미지만 보임 |

### 심각도
이 심각도 체계는 공식이 아니라 이 가이드라인의 운영 설계다. 3단계만 쓴다.
- **심각**: 그대로 내면 안 되거나 핵심 흐름을 크게 해치는 문제. 수정안이 필수다.
  - 앱인토스 미니앱이면 출시 불가 다크패턴 5개(아래 5-3).
  - 제품 핵심 가치를 훼손하는 문제, 접근성 기본 위반, 사용자가 선택지 없이 갇히는 문제.
  - 핵심 흐름의 완료율이나 이해를 크게 해칠 수 있는 문제. 핵심 가치를 뒷받침하는 정보가 가려지거나 묻힘.
- **중간**: 흐름은 끝나지만 인지·심리·노동 비용이 눈에 띄게 늘어나는 문제.
- **낮음**: 다듬으면 좋은 문제, 취향이 갈리는 문제, 영향이 작은 중복.

### 리포트 형식
지적마다 아래 여섯 항목을 쓴다.
- **화면**: 파일·위치
- **관찰**: 화면에서 직접 본 것
- **왜 문제인가**: 핵심 가치나 목표와 연결해서
- **근거 원칙**: 원칙 이름. 억지 연결이면 쓰지 않는다
- **제안**: 바로 고칠 수 있는 구체적 수정안 (순서·문구 예시 포함). 심각 지적은 수정안이 필수다
- **심각도**: 심각 / 중간 / 낮음

리포트 끝에 두 절을 붙인다.
- **잘 된 점**: 지켜진 원칙과 화면 근거. 검산한 사실(계산이 맞는지 등)도 여기에 쓴다.
- **확인 필요**: 화면만으로 알 수 없어 미확인인 것. 확인 방법도 함께 적는다.

## 5. 라이팅·에러·다크패턴·접근성 빠른 점검
문장 규칙의 자세한 내용은 ben-ux-writing(1절 참고)을 따른다. 여기는 설계 단계의 빠른 점검이다.

**5-1. 라이팅**
- 라이팅 코어밸류 5개(Clear·Concise·Casual·Respect·Emotional)를 기준으로 쓴다. 문장 규칙은 ben-ux-writing을 따른다.
- 눌렀을 때 일어날 일이 이름만으로 예측되는가? 제목이 이미 전한 말을 부제에서 되풀이하지 않았는가?
- 업계 용어·시스템 분류명을 사용자가 쓰는 말로 바꿨는가?
- 해줄 수 없을 때 이유보다 되는 조건을 먼저 말하는가? 강요하지 않고 권유하는가?
- 기쁜 일이나 큰 사건에는 정보만 주지 않고 그 사람의 감정에 먼저 반응하는가? (불안한 순간의 안심 문장은 Remove empty sentences와 부딪힌다. 부록 17절 6번)

**5-2. 에러**
- 에러 메시지는 다음 화면으로 넘어가게 안내하는 것이다. 공식 글(toss.tech, 좋은 에러 메시지를 만드는 6가지 원칙)의 6가지를 번호대로 옮긴다.
  ① 최고의 에러는 발생하지 않는 에러다. 발생하기 전에 막을 수 있는지 먼저 본다.
  ② 상황에 맞는 적절한 컴포넌트를 쓴다.
  ③ 스스로 해결할 방법을 안내한다. 가장 중요하다.
  ④ 사용자의 언어로 쓴다.
  ⑤ 쉽게 해결하도록 돕는다(행동 버튼, 입력값 재사용).
  ⑥ 부정 감정을 최소화한다.
- 에러 원칙은 근거 사례가 1건뿐이라 공식 글을 기준으로 삼는다.

**5-3. 다크패턴**
- 앱인토스 미니앱이면 아래 출시 불가 5개가 검수 기준이라 심각이다. 앱인토스가 아닌 제품은 출시 불가 기준이 아니므로, 같은 증상이어도 위 심각 정의에 해당할 때만 심각으로 보고 아니면 중간 이하로 판단한다.
- 출시 불가 5개: 진입 직후 바텀시트, 뒤로 가기 시 알림 동의 바텀시트, 선택지 없음, 예상치 못한 전면 광고, 모호한 CTA.
- 애원·호소형 감정 표현, 불필요한 느낌표, 불필요한 로딩 애니메이션을 쓰지 않는다. 한 화면에 핵심 그래픽은 하나만 둔다. (앱인토스 문서 기준)
- 모든 화면에 나가기 경로를 둔다. 권한을 거부해도 나머지 기능이 동작해야 한다.
- 선택 동의는 미리 체크하지 않고 "동의 / 동의 안 함"을 같은 비중으로 묻는다.

**5-4. 접근성**
- 4가지: 구조를 명확하게 · 의미를 정확히 · 예상 가능한 동작 · 시각 정보 보완.
- 색·모양·취소선처럼 시각으로만 전하는 의미는 말로 풀어 쓴 대체 텍스트로도 전한다.
- 시스템 글자 크기를 반영하고, 글자 크기를 하드코딩하지 않는다. (앱인토스/네이티브 화면에 적용하고, 그 외는 해당 디자인 시스템을 우선한다)
- 접근성 기본 위반은 심각으로 본다. 검증은 사용자의 실제 기기·스크린리더 환경에서 해야 하며, 정적 화면만 본 경우는 "확인 필요"로 남긴다.

## 6. 한계
- 사례와 원칙의 연결은 대부분 이 가이드를 만든 쪽의 해석이다. 연사가 원칙 이름을 직접 말한 명시 연결은 원칙별로 0~5건뿐이다.
- 2025판에서 빠진 4개(No Ads Patterns·Personalize·Sleek·Low-cost)가 지금도 유효한지는 이 자료로 알 수 없다. 사례가 가장 많은 Low-cost(원 자료 기준 57건)는 서로 다른 종류가 섞였을 수 있다.
- 근거가 얇은 항목(원 자료 기준): No Ads 4건, No More Loading 9건, 에러 원칙 1건, Easy to speak 1건.
- 같은 사례가 여러 원칙에 중복 등재돼 근거 수가 부풀어 있다. 원문 영상·글과 효과 수치는 직접 확인하지 못했고, `cases.md`의 수치는 발표 기준이다.
- 피드백 실험에서 사례를 쓰면 구체성이 늘지만 사실 과장이 섞일 수 있었다. 그래서 QA 절차 4번이 필수다.
- "원 자료 기준" 수치는 참고용이며 공개 근거는 `cases.md`의 178건이다.
- 이 가이드라인은 실제 작업에 쓰면서 틀린 판단은 고친다.
