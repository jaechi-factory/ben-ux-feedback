# 부록: 원칙별 상세 판단 규칙 · 위반 신호 · 근거 사례

`guideline.md`의 근거 자료예요. 필요한 원칙만 펼쳐 읽어요. 토스의 공개 자료를 학습해 만든 독립 자료이고 토스(비바리퍼블리카)와 제휴하거나 보증받은 관계가 아니에요.

## 읽는 법
- **공식 정의**는 토스 공개 제품 원칙의 2023판 검토 질문을 그대로 인용하고, 2025판 표현이 있으면 따로 적었다. 끝의 `[출처*]`는 토스 공개 자료(toss.tech mydoc 2023-09-03 등)를 뜻한다. 원칙별로 어느 문서에 실린 문구인지는 특정하지 못했다(미확인).
- **판단 규칙·위반 신호·대표 사례**는 공개 사례에서 귀납한 것이고 공식 문구가 아니다.
- **사례 번호**는 `C###` 형식이다. `cases.md`에서 번호로 장면 요약과 출처를 볼 수 있다. 같은 장면은 한 번호로 합쳤다.
- 공개 출처를 확보하지 못한 일부 예시는 사례 번호 없이 본문에만 적었다. 이런 규칙은 근거가 약한 것으로 본다.
- **태그**: `[일반]` 다른 제품에도 옮길 수 있음 / `[금융·규제]` 토스 금융·법적 요건 맥락 / `[업무도구]` 내부·B2B 도구 맥락. 태그는 사례 요약을 보고 붙였다.
- "원 자료 기준" 건수는 참고용이며 공개 근거는 `cases.md`의 178건이다.
- 효과 수치(전환율 등)는 옮기지 않았다. `cases.md`의 수치는 발표 기준이다. 사례 요약이 원문과 같은지는 직접 대조하지 못했다(미확인).
- 근거가 사례 1건뿐인 규칙은 "근거 1건"으로 표시했다.
- 순서는 `guideline.md`의 합친 목록(인지 6, 심리 5, 노동 3)을 따른다.

## 0. Simplicity (공식 core principle)
- **공식 정의**: "단순함은 토스 제품의 core principle 입니다." 사용자가 특별히 알아야 할 것, 배워야 할 것 없이 본능적으로 이해하는 상태이고, 이를 위해 인지·심리·노동 비용을 줄인다(toss.tech mydoc, 2023-09-03). 아래 판단 규칙은 사례에서 귀납한 것이다.
- **판단 규칙**
  1. 여러 서비스·구좌를 한곳에 모을 때는 서비스의 공통 속성이 아니라 사용자가 먼저 하려는 행동으로 묶고, 화면 하나에는 행동 하나만 둔다. 근거: C074 `[일반]`
  2. 좋은 노출 위치를 포기하라는 반대에 부딪히면, 성격이 다른 기능을 한 이름으로 묶어 그 자리를 지키고 있는지 보고, 그 유입이 가치를 이해하고 다시 찾아올 사람인지 되묻는다. 근거: C075 `[일반]`
  3. 복잡하게 얽힌 구조를 맡으면 사용자를 만나 흐름을 확인한 뒤 핵심 행위 두세 개만 남기고, 두 기능의 차이를 사용자가 모른 채 오가면 구조를 합치는 쪽을 의심한다. 근거: C018, C047 `[일반]`
  4. "당연히 알 텐데 / 원래 어려운 거라 / 실험이라 괜찮다"라는 말이 나오면 덜 쉬운 것으로 보고 출시 전에 사용자에게 다시 확인한다. 근거 1건: C166
- **위반 신호**: 홍보 구좌가 계속 늘어 우선순위가 안 잡힘(C074). 두 기능의 차이를 모른 채 오가거나 이탈함(C047).
- **대표 사례**: C074(문서 속성 대신 발급·납부·알림 확인 같은 행동으로 다시 묶음), C075(상단 고정 진입점을 포기하도록 설득함)
- **적용 시 주의**: 노출 위치를 포기하는 결정은 단기 유입 지표와 부딪힌다(M3 참고). 조직 구조 때문에 묶인 서비스에서 나온 판단이라 내 제품의 진입점 구조를 먼저 확인한다.

## 인지 비용

### 1. Casual Concept
- **공식 정의**: "어려운 금융의 개념을 친숙하고 이해하기 쉽게 만들었는가?" (2025판 영문의 우리말 요약: 복잡한 개념을 익숙하고 쉽게) `[출처*]`
- **판단 규칙**
  1. 모르는 이름·분류·숫자 기준을 보여줄 때는 이미 아는 대상(브랜드 로고, 일상 범주, 구체적 값)에 연결한다. 근거: C051, C052, C070, C141 `[일반]`
  2. 새 인터랙션이 사내 테스트를 통과해도 실제 사용률이 낮으면 튜토리얼을 덧붙이지 않고 사용자가 이미 아는 표준 컴포넌트로 바꾼다. 근거 1건: C164 `[일반]`
  3. 낯선 은유는 문구를 가리고도 알아보는지로 거르고, 이미 통하는 메타포는 형태를 유지한 채 감정 디테일만 올린다. 근거: C175, C174 `[일반]`
  4. 딱딱한 도메인이 시안에서 계속 무겁다는 피드백을 받으면 볼륨을 줄이는 대신 표현 방식 자체를 바꾸고, 연출 자원이 없으면 아이콘과 한 줄 문구로 전한다. 근거: C123, C124, C089 `[일반]`
  5. 사용자가 직접 입력·추적하던 값은 선택이나 자동 집계로 바꾸고, 익숙한 형태(주 단위 캘린더)로 보여준다. 근거: C109, C130 `[일반]`
  6. 같은 이름·모양의 컨트롤은 어떤 동작이 나은지 따지기 전에 모든 화면에서 같은 결과를 내게 맞춘다. 근거 1건: C143 `[업무도구]`
- **위반 신호**: 숫자 기준·전문 용어가 그대로 노출됨(C070 "만 7세", C052 산업분류). 사내 테스트는 통과했는데 실제 사용률이 낮음(C164 서랍식 달력). 문구를 가리면 알아보지 못함(C175). 같은 이름의 버튼이 화면마다 다르게 동작함(C143).
- **대표 사례**: C070("만 7세"를 "초등학생"으로 바꿈), C164(서랍식 달력을 익숙한 탭으로 교체)
- **적용 시 주의**: 원 자료 기준 23건이 모두 해석 연결이다. 금융 개념을 쉽게 푼 사례가 많아서 내 제품에서는 "사용자가 이미 아는 말"이 무엇인지부터 확인한다.

### 2. One Thing (One thing per One page)
- **공식 정의**: "하나의 화면에 하나의 명확한 목표가 들어가는가?" (2025판: "Each page should deliver a single, clear core message") `[출처*]`
- **판단 규칙**
  1. 여러 서비스·구좌를 한 화면에 모을 때는 사용자 행동 기준으로 묶고 화면 하나에는 행동 하나만 둔다. 근거: C074, C047 `[일반]`
  2. 홈에서 알리고 싶은 것이 늘어나면 지금 가장 먼저 확인할 한 가지를 정해 나머지의 시각 무게를 낮춘다. 목적이 하나의 행동인 화면은 핵심 값과 주 버튼만 남기고 부가 정보는 상세로 보낸다. 제목이 이미 전한 말은 화면 안에서 되풀이하지 않는다. 근거: C074, C063, C155 `[일반]`
  3. 입력이 귀찮은 항목이 여럿이면 화면을 나눠 한 번에 하나씩, 쉬운 질문부터 묻고 이미 가진 정보는 생략한다(구현이 복잡해져도 감수). 근거: C036, C100, C101 `[일반]`
  4. 여러 입력 수단·기능이 한 면에 동시에 노출되면 순서를 정하고, 우선순위가 낮은 기능은 첫 화면에서 빼서 사용 맥락이 익숙한 위치로 옮긴다. 근거: C066 `[일반]`
  5. 추천은 비교 목록 대신 가장 좋은 하나와 이유로 보여주고, 선택지를 늘려도 전환이 오르지 않으면 줄이는 안부터 검토한다. 단 어떤 사용자가 빠졌는지 확인한 뒤 확정한다. 근거: C086 `[일반]`
  6. 업무 도구는 확인할 일을 성격별 단계로 쪼개 순서를 한 방향으로 고정하고, 같은 유형의 건이 연속해서 나오게 큐를 나눈다. 근거: C077, C148, C100 `[업무도구]`
- **위반 신호**: 홍보 구좌가 계속 늘어남(C074). 여러 결제 수단이 한 면에 동시에 펼쳐져 어느 것이 먼저인지 추측해야 함(C066). 모든 버튼을 한 페이지에 두고 사용자가 외워야 함(C100). 홈에서 서로 다른 우선순위가 부딪침(C074).
- **대표 사례**: C074(개편 전 홈에서 "먼저 확인할 한 가지"를 정함), C100(주문·결제를 단계별 페이지로 나눠 한 화면에 할 일 하나만 둠)
- **적용 시 주의**: 줄일 수 없는 정보(법적 고지 등)가 있으면 삭제하지 않고 위계·순서·전달 방식을 바꾼다(`guideline.md` 3절 충돌 우선순위 3번 참고). 선택지 축소는 어떤 사용자가 빠지는지 확인한다.

### 3. Clear Action (Clear CTA)
- **공식 정의**: "과업을 완료하기 위한 CTA가 명확하게 드러나는가?" (2025판 영문의 우리말 요약: 원하는 결과를 위한 행동이 한눈에 보이는가) `[출처*]`
- **판단 규칙**
  1. 버튼·기능 이름은 사용자가 하는 동작 동사와 즉시성이 함께 읽히게 하고, 주변 화면을 보지 않아도 누르면 무슨 일이 일어나는지 알게 쓴다. 근거: C064, C177 `[일반]`
  2. 클릭을 유도하는 문구는 누른 뒤 나오는 화면과 얻는 것이 문구와 정확히 일치하게 하고, CTA가 광고처럼 읽히거나 눈에 안 띄지 않는지 사용자가 쓰는 장면에서 확인한다. 근거: C127, C013 `[일반]`
  3. 화면의 목적이 하나의 행동이면 핵심 값과 주 버튼만 남기고, 조건에 따른 분기는 사용자가 아니라 버튼 하나 뒤에서 시스템이 처리한다. 근거: C063, C054 `[일반]`
  4. 여러 사람이 이어 처리하는 업무는 상태마다 다음 행동(요청·승인)을 같은 화면에 붙이고, 외부 사용자 안내는 핵심만 말한 뒤 버튼 하나로 상세 확인과 답장까지 잇는다. 근거: C131, C080 `[업무도구]`
  5. 사용자가 거절하고 싶어 하는 선택 동의는 숨기거나 버튼을 막아 유도하지 말고 "동의 / 동의 안 함"을 같은 비중으로 묻는다. 다이얼로그에는 진행 버튼과 함께 닫기를 둔다. 근거: C007, C083 `[금융·규제]`
- **위반 신호**: CTA가 광고처럼 보여 지나침(C013). 버튼 이름이 주변 맥락에 기댐(C177 "선택"). 닫을 수 없는 팝업(C083). 입력 필드가 바로 활성화되는 첫 화면에서 제목을 읽기 전에 입력부터 하게 된다는 가설(C108. 가설이었고 첫 화면을 바꿔도 해결하지 못했다. 약한 근거).
- **대표 사례**: C064("지금 이자 받기"로 행동과 즉시성을 이름에 담음), C013("신용카드로 결제하기" 버튼이 광고처럼 보여 지나쳐짐)
- **적용 시 주의**: 5번은 동의 구조가 있는 금융·규제 맥락이다. 앱인토스 검수에서는 모호한 CTA가 출시 불가 다크패턴에 들어간다(`guideline.md` 5-3).

### 4. Simple Policy (Less Policy)
- **공식 정의**: "고객이 사용을 위해 '알아야 할' 것을 없앨 수 있는가?" (2025판: "An intuitive product starts with a simple policy.") 두 이름이 같은 원칙인지는 공식 자료도 미확정이다. `[출처*]`
- **판단 규칙**
  1. 선택지의 결과가 사용자에게 사실상 차이가 없으면 묻지 말고 기본값이나 정책으로 정하고, UI보다 상품·정책을 바꿀 수 있는지 먼저 따진다. 근거: C034, C146 `[일반]`
  2. 지표가 낮은 단계는 설명을 다듬기 전에 그 요구가 지금 정책에서도 필요한지, 다른 값에서 알 수 있는지, 대부분 같은 답인지 점검하고 이전 정책 때문에 남은 요구는 걷어낸다. 단 걷어내도 전환 상승을 기대하지 않는다(C105는 최종 전환율 차이 없음). 근거: C105, C057 `[일반]`
  3. 같은 화면의 배치·워딩 수정이 수십 번 반복돼도 풀리지 않으면 시안 작업을 멈추고 묶음 기준(제품 구조)이 틀렸는지 먼저 본다. 근거: C074 `[일반]`
  4. 큰 기능(권한 관리)이 필요해 보이면 사용자가 왜 실수하는지를 먼저 묻고, "OO님이 생성함" 같은 정보 표시 한 줄로 원인이 사라지는지 확인한다. 근거: C073, C034 `[업무도구]`
  5. 기존 관행이 조건을 붙이는 영역에서 조건을 없앨 때는 초기 반응이 약해도 조건을 되돌리지 않고 경험을 쪼갠 실험으로 개선한다. 근거 1건: C032 `[일반]`
- **위반 신호**: 이전 정책 때문에 남은 권한 요구(C105). 대부분 같은 답이 나오는 항목을 매번 물음(C057). 같은 화면을 수십 번 고쳐도 풀리지 않음(C074). 실수의 이유가 정보 부재인데 권한 기능을 계획함(C073).
- **대표 사례**: C034(신용카드 첫 화면의 선택지를 묻지 않고 정책으로 정함), C105(연락처 등 불필요한 권한 요구를 걷어냈지만 최종 전환율 차이 없음)
- **적용 시 주의**: 원 자료 기준 9건뿐이다. 정책 변경은 내 제품에서 사용자 지시나 사업 사실이 먼저 정해 둔 것이 있는지 확인한 뒤 제안한다.

### 5. Easy to Answer
- **공식 정의**: "과업 완료까지의 모든 질문은 3초 안에 대답할 수 있는 것들인가?" (2025판 영문의 우리말 요약: 어려우면 추천, 기억 안 나는 정보는 불러오기, 질문이 없는 게 최선) `[출처*]`
- **판단 규칙**
  1. 사용자가 선택 앞에서 머뭇거리면 결과를 모르는 것일 수 있으니, 방식을 고르게 하지 말고 지금 답을 아는 사실을 묻는다(예: "전문가 도움받을래, 직접 할래?" 대신 "서류 있어?", 이 예시는 사례 번호 없음). 없앨 수 없는 질문은 질문의 의도를 파악해 아는 말의 두 갈래 선택으로 바꾼다. 근거: C056 `[일반 / 후자는 금융·규제]`
  2. 사용자가 이미 아는 정보로 선택지를 좁힌다. 전체 목록 대신 해당하는 것만 보이고, 역할 같은 정보로 기본 선택을 미리 채우고, 가진 정보는 다시 묻지 않는다(예: 모든 보험사 대신 "내 보험사"만, 사례 번호 없음). 근거: C022, C036 `[일반]`
  3. 값을 직접 입력하다 이탈하거나 빈칸에서 오래 멈추면 선택지, 흔한 사례, 문장 시작을 보여줘 한 번에 답하게 한다. 근거: C109, C138, C140 `[일반]`
  4. 추천이 틀릴 수 있으면 하나를 고집하지 말고 후보를 모두 보이되 확률순으로 정렬하고, 정확도가 모자라면 후보 수를 늘려 최종 선택권을 사용자에게 남긴다. 근거: C050, C169 `[금융 예시, 방식은 일반]`
  5. 필드·필터 순서는 사용자가 정보를 확인·기록하거나 상대가 말하는 실제 순서에 맞춘다. 근거: C096, C133 `[업무도구]`
  6. 질문 순서는 직관으로 정하지 말고 안별 최종 전환율로 비교한다. 근거 1건: C037 `[일반]`
- **위반 신호**: 선택지 앞에서 머뭇거림. 빈칸에서 오래 멈춤(C138). 값을 직접 입력하는 단계에서 이탈함(C109). 입력 폼이 항목 수에 비례해 커짐(C020).
- **대표 사례**: "전문가 도움받을래, 직접 할래?"를 "서류 있어?"로 바꿈(사례 번호 없음), C169(계좌번호를 먼저 받고 은행을 1개에서 3개로 추천)
- **적용 시 주의**: 추천을 하나로 줄일지 여럿 보일지는 추천이 틀렸을 때의 위험 크기에 달려 보인다. 사례가 직접 정리한 기준은 아니고 해석이다.

### 6. Minimum Features
- **공식 정의**: "이 기능 없이는 절대 목표를 달성할 수 없나?" (2025판 영문의 우리말 요약: 기능 추가는 최후의 수단) `[출처*]`
- **판단 규칙**
  1. 사용자가 머뭇거리는 단계를 발견하면 빠르게 만들 방법이 아니라 없앨 수 있는지부터 묻고, 이미 입력한 정보로 추론해 채운다. 몰라도 되는 내부 개념은 상태별로 단계적으로 지운다. 근거: C169, C016 `[일반]`
  2. 큰 기능을 만들기 전에 가장 싼 수단(목업 제안서, 시트, 화면 없는 백엔드 MVP)으로 수요와 반복 빈도를 확인하고, 니즈가 도구의 한계를 넘을 때 제품으로 옮긴다. 근거: C102, C153, C071 `[일반]`
  3. 불확실한 부가 기능은 출시 전에 만들지 않고 가장 단순한 임시 대체로 두었다가 사용 흔적을 보고 추가한다. 근거: C072, C073 `[업무도구]`
  4. 지표가 낮은 단계에서는 가치를 못 주는 안내 화면을 제거 후보로 보되 이미 다른 채널에서 같은 정보를 받았는지 확인한다. 권한이나 편의 기능을 줄여도 전환 상승을 기대하지 않는다(C105·C106 모두 최종 전환율 차이 없음, C106은 발표자가 실패로 정리). 근거: C107, C106, C105 `[일반]`
  5. 쓰는 사람이 없는 기능이나 늘려도 효과가 없는 선택지는 줄이는 쪽을 먼저 검토한다. 근거: C104, C086 `[일반]`
  6. 서류를 받는 이유가 "확인"이면 조회·대행으로 대체하고 사용자에게는 동의만 받는다. 도움이 되려고 넣은 단계도 실제 사용 환경에서 못 하면 필요한 사람에게만 거치게 한다. 근거: C058, C035 `[금융·규제]`
- **위반 신호**: 사용 데이터가 0인 레이아웃이 남음(C104). 도움용 단계(신분증 촬영)를 이동 중에 못 해 이탈함(C035). 몰라도 되는 내부 개념이 홈에 노출됨(C016). 선택지를 늘려도 신청률이 같음(C086).
- **대표 사례**: C169("빨리 찾게"가 아니라 은행 선택 입력 자체를 없앰), C073(권한 관리 대신 "OO님이 생성함" 한 줄)
- **적용 시 주의**: 원 자료 기준 45건이 모두 해석 연결이다. 인트로나 안내 화면을 걷을 때는 Value First와 부딪히는지 본다(충돌 우선순위 5 참고).

## 심리 비용

### 7. Explain Why
- **공식 정의**: "왜 이 과업을 완료해야하는지 고객에게 충분히 설명했는가?" (2025판 영문의 우리말 요약: 왜 해야 하는지 명확히 설명했는가) `[출처*]`
- **판단 규칙**
  1. 동의·권한·정보 제공을 요청할 때는 왜 지금 필요한지 먼저 말하고 결제 같은 핵심 흐름과 분리하며, 사용자에게 이득이라 믿어도 미리 체크하지 않고 쉽게 거절할 출구를 둔다. 근거: C084, C081, C007 `[금융·규제]`
  2. 낯선 곳에서 연락이 가거나 자동화 결과를 사용자가 책임져야 하면 받기 전에 누가·언제·왜를 알리고, 입력의 출처를 확인할 기회를 남긴다. 근거: C150, C136 `[업무도구]`
  3. 새 개념의 버튼을 안 누르면 사용자 반응에서 "무엇을 모르는지"를 찾아 이유를 설명하는 보조 진입점을 두고, 개념을 모를 것 같으면 금액보다 개념 소개를 먼저 한다. 근거: C065, C127 `[일반]`
  4. 설명 화면을 더하기 전에 이름 변경, 직접 체험, 끝까지 보게 되는 연속 영상 같은 대안을 먼저 본다. 근거: C076, C002, C028 `[일반]`
  5. 입력하는 지점에서 용도를 한 줄로 알리고(누가 볼 수 있는지), 참여를 요청할 때는 "왜 묻나 / 내 의견은 어떻게 되나"에 미리 답하며, 외부 링크로 들어온 화면은 미리보기의 약속을 첫 화면에서 한 번 더 확인시킨다. 근거: C165, C044, C091 `[일반]`
- **위반 신호**: 결제 도중 오픈뱅킹 재동의 팝업이 뜸(C084). 누르지 않은 항목이 미리 체크됨(C081). 새 개념의 버튼을 일부만 누름(C065). 입력 필드가 바로 활성화되는 첫 화면이 지금 하는 일을 알리지 않는다는 가설(C108. 가설이었고 해결하지 못했다. 약한 근거).
- **대표 사례**: C084(결제 흐름 중 재동의 팝업은 이유를 먼저 말하고 분리해야 하는 사례), C065(적게 눌린 버튼 옆에 이유를 설명하는 보조 진입점을 둠)
- **적용 시 주의**: 1번은 규제된 동의 구조 안에서 나온 규칙이다. 규제가 없는 제품에서도 "미리 체크하지 않기"와 "쉬운 거절"은 그대로 쓴다. 불안한 지점에서는 설명이 우선이고, 반복되는 설명은 뺀다(충돌 우선순위 4).

### 8. Value First
- **공식 정의**: "뭐가 좋은지도 모르는데 정보 입력을 요구하거나 비용을 이야기하진 않는가?" (2025판 영문의 우리말 요약: 시간과 돈을 들일 가치가 있음을 먼저 보여줌) `[출처*]`
- **판단 규칙**
  1. 줄일 수 없는 긴 입력·인증 퍼널 앞에서는 단계를 줄일 생각만 하지 말고 치르면 얻을 이익을 실제 데이터 모양의 예시 화면으로 먼저 보인다. 동의·약관 단계에서 이탈이 보이면 사용자가 가치를 체감한 직후로 옮기되, "인트로 제거 = 전환 상승"으로 일반화하지 않고 실험으로 확인한다. 근거: C168, C090 `[금융 예시, 방식은 일반]`
  2. 정보를 모아 보여주는 것이 가치인지 의심되면 그 정보가 사용자의 실제 업무 흐름·이득에 연결되는지로 재정의하고, 눌렀을 때 실제 내용이 나오는지까지 확인한다. 근거: C068, C015 `[일반]`
  3. 공급 측 사용자가 모이지 않으면 편의 기능을 더하지 말고 그 사용자가 평소 가장 못 얻던 것을 직접 주며, 목표를 끝낸 직후 다음 행동에도 별도 혜택을 붙인다. 근거: C024, C031 `[양면 시장·비즈니스 맥락]`
- **위반 신호**: 눌러도 "내역 없음"이 나옴(C015). 약관·동의 단계에서 이탈이 큼(C090). 긴 조회 퍼널 앞에 이익을 보여주는 화면이 없음(C168). 공급 측 사용자가 안 모임(C024).
- **대표 사례**: C168('내 보험' 조회 앞에 예시 데이터 가치 화면을 추가), C090(약관을 인트로가 아니라 정답 직후로 옮김)
- **적용 시 주의**: 3번은 양면 시장 맥락이라 일반 제품에는 맞지 않을 수 있다. 가치 화면을 더하는 것은 Minimum Features와 부딪힐 수 있으니 줄일 수 없는 긴 퍼널일 때만 쓴다.

### 9. Context Based
- **공식 정의**: "앞 뒤 상황의 맥락이 이어지는가?" (2025판 영문의 우리말 요약: 전체 사용자 여정을 고려했는가) `[출처*]`
- **판단 규칙**
  1. 정기 알림은 사용자의 상황이 나쁠 때(매출 0원)와 이미 해결해 뒀을 가능성(납부일 푸시)을 먼저 따지고, 확인되지 않은 뉘앙스로 불안을 만들지 않는다. 근거: C038, C082 `[일반(금융 푸시 사례)]`
  2. 사용자가 나중에 해야 할 일은 기억에 맡기지 말고 필요한 시점에 이미 쓰는 채널로 알리고, 알림 안에서 바로 다음 행동을 하게 한다. 상태 변화를 기다리는 업무는 시스템이 감지해 할 일을 올린다. 근거: C152, C078 `[업무도구]`
  3. 기능을 새로 놓을 때는 사용자가 이미 쓰는 장소·도구·창 배치를 먼저 관찰해 그 안에 둔다. 근거: C095, C019, C021 `[업무도구]`
  4. 자동화나 CTA를 더할 때는 매일 쌓였을 때의 화면과 사용자가 실제로 쓰는 장면에서 어떻게 보이는지 확인한다. 근거: C062, C013 `[일반]`
  5. 사용자가 가장 기다리는 순간이 화면 밖(내부 심사)에 있으면 내부 도구까지 디자인 범위로 보고, 신규 화면은 의존 시스템이 준비된 시점에 맞춰 적용하며 그 전에는 구 화면을 선택할 수 있게 둔다. 근거: C059, C145 `[금융·업무도구]`
  6. 타겟이 우리와 나이·문화가 멀면 "그 집단이라면 이럴 것"이라는 시장의 문법을 따르지 말고 그 집단이 스스로를 어떻게 보는지부터 확인한다. 근거: C110, C113 `[일반]`
- **위반 신호**: 매출이 0원인 사용자에게도 정기 매출 알림이 감(C038). 납부일 푸시가 이미 해결한 사용자에게 연체 뉘앙스를 줌(C082). 신규 화면이 아직 준비되지 않은 시스템을 전제로 만들어짐(C145). 콘텐츠를 여러 채널에 노출해도 만든 팀만 봄(C011).
- **대표 사례**: C038(매출 0원 시기에 매출 알림을 끔), C152(재통화를 외우게 하지 않고 10분 전 메신저로 알림)
- **적용 시 주의**: 원 자료 기준 45건 중 업무 도구 맥락이 많다. 알림 사례는 금융 푸시이므로 내 제품의 알림 채널과 사용자 상황을 먼저 확인한다.

### 10. No Ads Patterns (2023판에만 있음)
- **공식 정의**: "습관적으로 광고 문법으로 소구하고 있지는 않은가?" `[출처*]`
- **판단 규칙** (원 자료 기준 사례가 4건뿐이고 1건은 규칙이 비어 있어 2개만 적는다.)
  1. 클릭을 유도하는 문구는 광고냐 아니냐를 위치·형식이 아니라 문구가 약속한 것과 누른 뒤 결과의 일치로 판단하고, CTA가 광고처럼 읽히지 않는지 사용자가 쓰는 장면에서 본다. 근거: C127, C013 `[일반]`
  2. 이탈을 막는 안내에서는 잃을 것을 경고하지 않고 사실만 남긴 뒤 닫기와 나가기를 같은 무게의 선택으로 준다. 근거 1건: C157. 같은 방향의 관련 사례: C081(미리 체크하지 않기) `[일반]`
- **위반 신호**: 누른 뒤 화면이 문구의 약속과 다름(C127). CTA가 광고처럼 보여 지나쳐짐(C013). 이탈 안내가 손해 프레임임(C157).
- **대표 사례**: C127("확실함이 깨지면 광고"라는 기준), C157(이탈 안내를 중립 문구로)
- **적용 시 주의**: 2025판에서 빠진 원칙이다. 앱인토스 검수의 다크패턴 기준(`guideline.md` 5-3)이 별도로 있어 그쪽이 우선한다.

### 11. Personalize (2023판에만 있음)
- **공식 정의**: "고객에게 맞춤 경험을 제공했는가?" `[출처*]`
- **판단 규칙**
  1. 사용자가 모르는 값을 요구해야 할 때는 이미 가진 행동 이력이나 역할로 후보나 기본 선택을 채우고 선택만 하게 한다. 오답 위험은 틀려도 실행 단계에서 막히는 안전장치가 있는지로 판단한다. 근거: C050, C022 `[일반]`
  2. 추천이 틀릴 수 있으면 하나만 고집하지 말고 후보를 모두 보이되 맞을 확률순으로 정렬한다. 근거: C050 `[일반]`
  3. 복잡한 도메인은 일반 정보 대신 사용자의 지금 상황별로 쪼개 보여주고 그 자리에서 다음 행동을 잇는다. 관심이 낮은 상품에 선택지가 많으면 줄이기보다 현재 상태를 먼저 묻고 가까운 것만 보인다. 근거: C026, C088 `[금융(보험·상품) 예시, 방식은 일반]`
  4. 항목이 많아 어지러우면 가장 자주 하는 행동 한두 개만 고정하고, 덜어낸 빈자리에는 그 순간의 맥락에 맞는 한 가지만 올린다. 근거: C014, C017 `[일반]`
  5. 취향이 갈리는 타겟은 한 정답을 고집하지 않고 페르소나별 선택지 세트로 나누며, 취향 조합은 실물 샘플의 선호도 수집으로 정한다. 근거: C111, C114, C116 `[일반(굿즈·카드 디자인)]`
- **위반 신호**: 이미 가진 정보를 다시 물음(C036). 아는 항목을 전체 목록에서 찾게 함. 선택지가 많은 관심 낮은 상품에서 전환이 안 옴(C088). 타겟이 멀어도 시장의 기본 문법을 그대로 따름(C110).
- **대표 사례**: 모든 보험사 목록 대신 "내 보험사"만 보임(사례 번호 없음), C050(동명이인 후보를 모두 보이되 확률순으로 정렬)
- **적용 시 주의**: 2025판에서 빠진 원칙이고 원 자료 기준 25건이 모두 해석 연결이다. 맞춤은 "아는 정보로 묻지 않기·좁히기"일 때 채택되었고, Minimum Features와 부딪히면 이 방향으로 푼다(부록 17절 2번).

## 노동 비용

### 12. Sleek Experience (2023판에만 있음)
- **공식 정의**: "전체 Flow가 물 흐르듯이 진행되는가?" `[출처*]`
- **판단 규칙**
  1. 사용자가 다른 곳에서 값을 복사해 붙이거나 도구 사이를 오가면 같은 화면에서 검색·선택 한 번으로 끝나게 한다. 근거: C171, C151 `[업무도구]`
  2. 입력 화면은 값의 형식에 맞는 키보드로 열고, 유일한 할 일이 입력이면 진입과 동시에 포커스를 준다. 근거 사례 번호 없음 `[일반]`
  3. 사용자가 직접 준비해야 하는 선행 작업은 이미 가진 데이터와 연결로 시스템이 대신 채운다. 근거: C055, C058 `[금융]`
  4. 상태가 바뀌기를 기다리며 반복 확인하는 업무는 시스템이 조건 충족을 감지해 할 일을 올리고, 반복 승인은 한 클릭으로 줄인 뒤 연동으로 없앤다. 근거: C078, C021 `[업무도구]`
  5. 사용자가 개별로 바꿀 수 없는 항목에는 조작 가능해 보이는 컨트롤을 반복해 두지 말고, 선행 조건이 있는 선택지는 비활성 표시로 지금 할 수 있는 행동만 눈에 띄게 한다. 근거: C009 `[금융·규제]`
  6. 모션·피드백은 공수가 작고 모두가 매일 닿는 기본 동작(터치·탭·전환)부터 바꾸고, 제스처로 시작되는 대기 표시는 제스처와 그래픽이 하나의 연속된 움직임으로 보이는지 확인한다. 근거: C120, C170 `[일반]`
- **위반 신호**: 복사·붙여넣기를 반복함(C171). 도구 이동·복사 포함 23단계(C151). 입력할 값과 키보드 종류가 안 맞음(사례 번호 없음). 아이폰 웹에서 연속 탭 시 약관 체크 누락(C004).
- **대표 사례**: C151(23단계를 7단계로 줄임), 인증번호 화면을 숫자 키보드로 시작(사례 번호 없음)
- **적용 시 주의**: 2025판에서 빠졌고 원 자료 기준 38건이 모두 해석 연결이다. 업무 도구 사례가 많아서 소비자용 화면에는 2번과 6번이 가장 옮기기 쉽다.

### 13. Low-cost Action (2023판에만 있음)
- **공식 정의**: "노동 비용이 더 적게 드는 경험을 만들었는가?" `[출처*]`
- **판단 규칙**
  1. 사용자가 불안해서 밖에서 하던 확인이나 시스템 제약으로 막힌 순간의 처리는 제품이 아는 정보로 대신하고 결과를 한 신호로 보인다. 근거: C040, C041 `[금융]`
  2. 참여나 반복 승인의 부담은 운영자가 먼저 흡수하거나 사용자가 이미 쓰는 도구에서 한 번 클릭으로 줄인 뒤 연동으로 없앤다. 근거: C012, C021 `[업무도구]`
  3. 해결책이 다른 곳에서 해야 하는 일이면 문구 안내로 끝내지 말고 행동 버튼을 붙이고, 실패가 반복되면 우회 경로를 더 강하게 제안하되 방금 입력한 값을 재사용한다. 근거: C162, C049 `[금융 예시, 방식은 일반]`
  4. 반복 작업은 공통 골격과 달라지는 조각으로 나눠 조합하거나 자동화한다. 단 조합 방식은 앞 단계가 통일돼 있어야 쓸 수 있다. 근거: C079, C172, C135 `[업무도구]`
  5. 실수가 반복되면 전달을 더 정확하게 하기보다 내용을 가장 잘 아는 사람이 직접 설정하게 해 전달 단계를 없애고, 막지 못하는 실수는 배포 없이 즉시 수정할 경로를 만든다. 근거: C147 `[업무도구]`
  6. 기존 도구를 대체할 때는 사용자의 실제 목적과 트리거(단축키 등)를 그대로 가져오고 약점만 고치며, 입력 순서도 사용자의 확인 순서에 맞춘다. 근거: C097, C096 `[업무도구]`
- **위반 신호**: 불안해서 앱 밖에서 확인함(C040). 은행 점검 때문에 기다림과 지식을 요구함(C041). 해결 행동은 다른 곳인데 문구만 있음(C162). 자동 지급 알림이 쌓여 핵심 정보를 가림(C062).
- **대표 사례**: C040(사기 의심 계좌 조회를 복잡한 화면 대신 아이콘 하나로), C041(은행 점검 시간에 기다리게 하지 않고 예약으로 처리)
- **적용 시 주의**: 가장 큰 묶음(원 자료 기준 57건)이라 서로 다른 종류의 사례가 섞였을 수 있다. 자동화는 사용자가 결과를 책임지고 인지할 수 있는 지점까지만 한다(충돌 우선순위 2).

### 14. No More Loading
- **공식 정의**: "핵심 Flow 에서 기다림을 완전히 없앴는가?" (2025판 이름도 No More Loading) `[출처*]`
- **판단 규칙**
  1. 긴 대기가 불안을 만드는 처리는 대기 화면을 꾸미기 전에 기다릴 필요가 없는 구조인지 확인하고, 그렇다면 홈으로 보내면서 끝나면 알린다고 말한다. 대기가 화면 밖(내부 심사)에 있으면 그 시간을 줄이는 것도 디자인으로 본다. 근거: C048, C059 `[금융]`
  2. 연결 수는 늘었는데 전환이 낮으면 응답 지연 구간별 전환율을 비교하고, 지연이 원인이면 비동기 흐름을 실시간으로 바꾼다. 근거 1건: C027 `[양면 시장 맥락]`
  3. 기다려야 하는 화면은 가짜처럼 보이는 정보 대신 믿을 수 있는 실제 정보를 보여준다. 근거: C160 `[일반]`. (시안과 구현 화면을 로딩·키보드 같은 실제 조건에서 대조해 점검하는 것은 사례 번호 없는 규칙이라 근거가 약하다.)
  4. 모션이 성능 때문에 반대에 부딪히면 모션을 빼기 전에 측정하고 렌더링 방식을 바꿔 둘 다 지킬 수 있는지 먼저 본다. 근거 1건: C005 `[일반]`
- **위반 신호**: 7분 심사 대기처럼 사용자가 기다려야 함(C048). 응답 지연 구간에서 전환이 떨어짐(C027). 작업 대상 확인에 화면을 4~5번 왕복함(C134). 로딩 화면의 정보가 가짜처럼 보인다는 인터뷰 힌트(C160).
- **대표 사례**: C048(7분 심사 대기를 홈으로 돌려보내고 끝나면 알림), C027(응답 시간 데이터로 3초 실시간 연결을 설계)
- **적용 시 주의**: 원 자료 기준 9건뿐이다. 앱인토스 검수는 인터랙션 지연을 2초 미만으로 요구한다. 정적 화면만으로는 실제 지연을 알 수 없어서 QA에서는 "확인 필요"로 남긴다.

## 15. 라이팅 원칙 (설계 단계 참고)
- **공식 정의**: 라이팅 8원칙(Predictable hint · Weed cutting · Remove empty sentences · Focus on key message · Easy to speak · Suggest over force · Universal words · Find hidden emotion)과 5 코어밸류(Clear · Concise · Casual · Respect · Emotional)의 이름만 공식 자료에서 확인했고 본문 정의는 인용하지 못했다. 문장 규칙은 ben-ux-writing(`guideline.md` 1절 참고)이 맡는다. `[출처*]`
- **판단 규칙**
  1. **Predictable hint**: 버튼·입력칸·기능 이름은 눌렀을 때 또는 입력했을 때 일어날 일이 이름만으로 예측되게 쓰고 최종 혜택은 라벨에 넣지 않는다. 근거: C154, C177, C165, C142 `[일반]`
  2. **Weed cutting**: 줄일 수 없는 문구·질문은 내용 대신 구조를 바꾼다(글자 크기·굵기로 위계, 아는 말의 두 갈래 선택, 망설이는 선택은 기본값, 무거운 단어는 가볍게). 근거: C008, C056, C139 `[금융·규제 / 일반]`
  3. **Remove empty sentences**: 제목이 이미 전한 말은 부제로 되풀이하지 않고 허전해도 채우지 않으며, 알림은 한 건에 핵심 한두 가지만 담는다. 근거: C155, C098, C142 `[일반]`
  4. **Focus on key message**: 선택지는 차이가 라벨에서 바로 읽히게 하고 배경 설명은 뺀다. 사용자가 대상을 모를 때는 이름보다 의미 있는 수치와 한 줄 설명을 앞세운다. 근거: C156, C093, C039 `[일반]`
  5. **Universal words**: 업계 관용어·시스템 분류명·전문 용어는 사용자가 쓰는 말이나 손에 든 대상의 상태로 바꾸고, 한 줄 알림은 직접 받아 보는 테스트를 반복한다. 근거: C094, C161, C158, C053 `[일반(증권·신분증 예시는 금융)]`
  6. **Suggest over force**: 해줄 수 없을 때는 이유보다 되는 조건을 먼저 말하고, 이탈 안내는 중립으로, 팀 규칙은 금지 목록보다 긍정문으로 쓴다. 근거: C163, C157, C085 `[일반]`
  7. **Find hidden emotion**: 큰 의미가 있는 사건(완납·기쁜 일)에는 정보만 알리지 말고 그 사람의 노력이나 겪은 불편에 먼저 반응하고, 정답 없는 감성 카피는 당사자를 포함한 여러 사람에게 보여 불편하게 읽힐 표현을 고친다. 근거: C159, C060, C061, C118 `[일반(금융 푸시 사례 다수)]`
  8. **Easy to speak**: 근거 1건: C064(동작 동사와 즉시성, 반복 주기 같은 속성은 이름에서 뺌).
  9. **접근성(대체 텍스트)**: 색·모양·취소선처럼 시각으로만 전하는 의미는 역할·상태·속성을 말로 풀어 쓴 대체 텍스트로 만들고, 검증은 사용자의 실제 기기·스크린리더 환경에서 한다. 근거: C003, C176, C125 `[일반]`
- **위반 신호**: 버튼 이름이 주변 화면 없이는 의미가 안 통함(C177). 제목과 부제가 같은 말을 함(C155). 업계 용어가 그대로 나감(C053 "VI(변동성 완화장치)"). 알림이 확인되지 않은 연체 뉘앙스를 줌(C082). 이탈 안내가 손해 프레임임(C157).
- **대표 사례**: C159(대출 상환 푸시에서 정보 뒤의 감정을 찾음), C163("이용할 수 없는 연령"을 "만 19세 이상부터 확인할 수 있어요"로)
- **적용 시 주의**: 에러 원칙은 사례 근거가 C043 한 건뿐이라 규칙을 적지 않았다. 에러는 공식 글의 6가지(`guideline.md` 5-2)를 기준으로 쓴다. 불안한 순간의 "안심 문장"은 Remove empty sentences와 부딪힌다(부록 17절 6번).

## 16. 원칙 밖 판단 패턴 전체 (12개)
사례가 아니라 원고 메모인 항목이 섞여 있다. 경계가 애매한 항목은 가까운 쪽에 넣었다. 일부 항목은 사례 번호 없이 세션 단위 메모만 있어 번호를 적지 않았다.

| # | 패턴 | 설명 | 근거 사례 | 공식 원칙과의 관계 |
|---|---|---|---|---|

## 17. 원칙끼리 부딪힐 때 전체 (6개)
"사례 결론"은 사례가 직접 말한 판단이고, "읽은 경향"은 사례들을 나란히 보고 정리한 해석(추정)이에요.

1. **One Thing(줄이기) vs 정보 완전성(줄일 수 없는 내용)**
   - 읽은 경향: 내용은 고정하고 구조·전달을 바꿔 인지 비용을 낮춘다.
   - 근거: C008(위계로 복잡해 보임을 낮춤), C029(내용은 두고 스크롤·음성·제스처로), C056(없앨 수 없는 질문을 쉬운 선택으로), C063(부가 정보는 삭제가 아니라 한 단계 뒤로). `[금융·규제 색채가 강함]`
2. **Minimum Features vs Personalize**
   - 사례 결론: 자동 입력·알림 권한까지 걷어낸 실험은 최종 전환율 차이가 없었고 발표자가 실패로 정리했다(C106). 편의 기능이 전환을 올린다고 가정하지 않는다.
   - 읽은 경향: 맞춤은 "이미 아는 정보로 묻지 않기·좁히기"일 때 채택된다(C022, C036). 덜어낸 빈자리에는 그 순간 맥락의 한 가지만 올린다(C017). 선택지 수는 줄이되 어떤 사용자가 빠졌는지 확인하고 추천형으로 푼다(C086 → C088).
3. **Low-cost Action(자동화) vs 사용자 통제감·Suggest over force**
   - 사례 결론: 자동화 범위는 효율 최대 지점이 아니라 사용자가 결과를 책임지고 인지할 수 있는 지점까지다(C136).
   - 근거: C136(100% 자동화에 사용자가 불안해함, 확인 대상을 결과물에서 입력으로), C062(자동 지급이 쌓이면 사용자가 시작하는 방식으로 되돌림), C081(미리 체크한 백업).
4. **Value First(가치 화면 추가) vs Minimum Features(단계 제거)**
   - 읽은 경향: 단계를 늘리는 쪽은 "줄일 수 없는 긴 퍼널"일 때만이고, 그 외에는 가치를 못 주는 단계를 제거한다.
   - 근거: C168(예시 데이터 가치 화면 추가) vs C107(가치 없는 인트로 제거). C090은 "인트로 제거 = 전환 상승"으로 일반화하지 말라고 하고, C107은 이미 스토어에서 같은 정보를 받았는지 확인하라고 한다.
5. **전환 지표 vs 사용자의 거절 가능성**
   - 사례 결론: 사용자를 막는 대신 거부를 쉽게 했더니 동의율도 올랐다는 결과를 연사가 직접 정리했다(C007).
   - 근거: C157(이탈 안내를 중립으로), C081(미리 체크하지 않기), C032(다크 패턴 대신 사용자가 부담을 떠안지 않는 길, 비용은 팀이 감수). 우선순위는 거절 가능성 > 단기 전환이다.
6. **설명 줄이기(Remove empty sentences·이해할 일 없애기) vs 설명 더하기(Explain Why)**
   - 읽은 경향: 반복되는 말은 빼고, 불안·낯섦이 있는 지점(동의, 낯선 연락, 새 개념)에서는 설명이 먼저다.
   - 근거: C155(제목 되풀이 금지), C142(설명·제목을 빼고 한 줄 질문으로) vs C084, C150, C065. 불안한 순간에 "없어도 되는 안심 문장"을 일부러 넣는다는 발표자 언급도 있다(사례 번호 없음, 화면 확인 안 됨).

## 18. 약한 근거 요약
- 아래 건수는 참고용이며 공개 근거는 `cases.md`의 178건이다.
- 명시 표기는 원 자료 색인 468건 중 25건뿐이다. 해석만 있는 원칙(명시 0): Casual Concept 23, Minimum Features 45, Context Based 45, Personalize 25, Sleek 38, Low-cost 57, No More Loading 9, No Ads 4, Easy to speak 1, Weed cutting 4, 접근성 3, 에러 1.
- 같은 사례가 여러 원칙에 중복 등재돼 색인 합계 468에 비해 원 자료의 사례 카드는 323장이다. 증거가 부풀려져 있다. 이 부록이 근거로 든 것은 그중 합쳐서 `cases.md` 178건이다.
- 일부 예시(서류 있어?, 내 보험사 등)는 공개 출처의 장면을 확인하지 못해 사례 번호 없이 본문에만 남겼다. 이 규칙들은 더 약한 근거로 본다.
- 서로 긴장이 있는 규칙: 인트로 제거(C107, C139) vs 가치 화면 추가(C168). 단일 추천(사례 번호 없음) vs 후보 여러 개 노출(C050, C169). 지표 우선(C119) vs 지표 앞에서 사람 확인(C081~C085). 라이팅 품질 일부 포기(C167) vs 사용자 노동 이전의 책임(C034~C037).

- 원본 영상·글 79개, 사례 카드 323장의 원문, 이미지·영상은 직접 보지 못했다. 12개 메타 패턴 배정은 항목 이름과 설명만 보고 나눈 것이라 경계가 달라질 수 있다.
